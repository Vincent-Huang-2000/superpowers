# 系统化调试

## 概述

**核心原则** 每次都要先找到根因，再尝试修复。只消除表象就算失败。

**违反这套流程的明文要求，就违背了调试的宗旨。**

## 铁律

```
任何修复都必须先经过根因调查
```

第一阶段尚未完成时，不能提出修复方案。

## 何时使用

适用于任何技术问题，包括以下情况。
- 测试失败
- 生产环境缺陷
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其要在以下情况下使用**
- 时间紧迫（紧急情况容易让人靠猜测行事）
- 看起来「随手改一下」就能解决
- 已经试过多种修复方案
- 上一次修复没奏效
- 还没有完全弄清问题

**以下情况也要遵循流程**
- 问题看起来很简单（简单缺陷也有根因）
- 正在赶时间（仓促修改一定会造成返工）
- 负责人要求立即修好（系统排查比反复试错更快）

## 四个阶段

必须完成当前阶段，才能进入下一阶段。

### 第一阶段：调查根因

**尝试任何修复前，先完成以下步骤**

1. **仔细阅读错误信息**
   - 每条错误和警告都要看
   - 这些信息往往直接指出解决办法
   - 读完整的堆栈跟踪
   - 记下行号、文件路径和错误码

2. **稳定复现**
   - 能稳定触发问题吗？
   - 具体步骤是什么？
   - 每次都会发生吗？
   - 如果无法复现，先收集更多数据，避免猜测

3. **检查近期改动**
   - 哪些改动可能引发这个问题？
   - 查看 Git 差异和近期提交
   - 检查新依赖和配置变更
   - 核对环境差异

4. **在多组件系统中收集证据**

   **系统有多个组件时适用，例如 CI → 构建 → 签名，或 API → 服务 → 数据库**

   **提出修复方案前，先添加诊断日志和检查**
   ```
   对每个组件边界执行以下检查。
     - 记录组件接收到的数据
     - 记录组件输出的数据
     - 验证环境变量和配置是否正确传递
     - 检查每一层的状态

   先运行一次，收集能指出故障位置的证据
   再分析证据，确认哪个组件出了问题
   接着深入调查该组件
   ```

   **多层系统示例**
   ```bash
   # 第 1 层：工作流
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: $([ -n "${IDENTITY:-}" ] && echo SET || echo UNSET)"

   # 第 2 层：构建脚本
   echo "=== Env vars in build script: ==="
   printenv IDENTITY >/dev/null 2>&1 && echo "IDENTITY in environment" || echo "IDENTITY not in environment"

   # 第 3 层：签名脚本
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **据此定位故障层级** 例如机密变量 → 工作流 ✓，工作流 → 构建 ✗。

5. **追踪数据流**

   **错误发生在调用栈深处时**

   同目录中的 `root-cause-tracing.md` 说明了完整的反向追踪方法。

   **简要步骤**
   - 异常值从哪里产生？
   - 哪个调用方把异常值传到了这里？
   - 继续向上追踪，直到找到源头
   - 在源头修复

### 第二阶段：分析模式

**修复之前，先找出相关模式**

1. **查找正常工作的示例**
   - 在同一代码库中找到类似且正常工作的代码
   - 哪段正常代码与出问题的代码相似？

2. **对照参考实现**
   - 如果要实现某种模式，完整阅读它的参考实现
   - 逐行细读
   - 彻底理解这种模式后再应用

3. **找出差异**
   - 正常的情况和出错的情况有哪些不同？
   - 列出每一处差异，再小也要记下
   - 避免想当然地认定「这点差异不可能有影响」

4. **弄清依赖**
   - 这里依赖哪些其他组件？
   - 需要哪些设置、配置和环境条件？
   - 它依赖哪些前提假设？

### 第三阶段：提出并检验假设

**按科学方法检验**

1. **一次只提出一个假设**
   - 清楚表述「我认为 X 是根因，依据是 Y」
   - 把假设写下来
   - 写得具体明确

2. **用最小改动检验**
   - 只做能检验假设的最小改动
   - 每次只改变一个变量
   - 避免同时修复多个问题

3. **核实结果后再继续**
   - 试验结果支持假设吗？支持就进入第四阶段
   - 结果不支持假设，就提出新的假设
   - 切勿在现有改动上继续叠加修复

4. **遇到不懂的地方**
   - 明确说「我还不理解 X」
   - 如实说明自己知道多少
   - 请求帮助
   - 继续查证

### 第四阶段：实施修复

**针对根因实施修复**

1. **编写会失败的测试用例**
   - 使用最简单的复现方式
   - 尽可能编写自动化测试
   - 没有测试框架时，编写一次性测试脚本
   - 必须在修复前写好测试
   - 使用 `superpowers:test-driven-development` 技能编写合适的失败测试

2. **只实施一项修复**
   - 解决已经定位的根因
   - 每次只做一项改动
   - 避免「顺手」做其他改进
   - 避免把重构捆绑进来

3. **验证修复**
   - 测试现在通过了吗？
   - 其他测试都仍然通过吗？
   - 问题确实解决了吗？
   - 在宣称修复成功前，使用 `superpowers:verification-before-completion` 技能

4. **如果修复未奏效**
   - 停下来
   - 数一数已经尝试了几次修复
   - 次数 < 3 时，回到第一阶段，根据新信息重新分析
   - **次数 ≥ 3 时，停下来审视架构（见下方第 5 步）**
   - 先讨论架构，再考虑第 4 次修复

5. **三次或以上修复失败时，审视架构**

   **以下现象表明架构可能有问题**
   - 每次修复都在其他位置暴露出新的共享状态、耦合或其他问题
   - 每次修复都需要「大规模重构」才能落实
   - 每次修复都会在别处引发新症状

   **停下来，重新审视基本设计**
   - 这种模式本身合理吗？
   - 我们是不是仅仅出于惯性才继续沿用它？
   - 该重构架构，还是继续逐个处理症状？

   **先和用户讨论，再尝试进一步修复**

   这说明架构本身有问题，需要重新审视设计。

## 遇到警示信号就停下

留意以下想法或做法。
- 「先快速修一下，之后再查」
- 「先改一下 X，看看管不管用」
- 「一起改几处，再跑测试」
- 「跳过测试，我手动验证就行」
- 「大概是 X，我先去改」
- 「还没完全搞懂，但这样也许能行」
- 「参考模式是 X，不过我打算换种写法」
- 「主要问题有这些：[未经调查就列出修复方案]」
- 还没追踪数据流就提出修复方案
- **「再试一次修复就好」（已经尝试至少两次）**
- **每次修复都在别处暴露出新问题**

**出现任何一项，都要停下来，回到第一阶段。**

**三次或以上修复失败时** 审视架构（见第四阶段第 5 步）。

## 用户提示排查偏离方向时

**留意用户的这些提醒**
- 「实际情况不是这样吗？」表示你作了未经核实的假设
- 「这样能让我们看到……吗？」表示你本该先收集证据
- 「别猜了」表示你还没搞懂问题就在提修复方案
- 「再往深处想一层」表示需要审视基本设计
- 「我们卡住了吗？」（感到沮丧时）表示当前做法没有奏效

**收到这类提醒时** 停下来，回到第一阶段。

## 常见借口及应对

| 借口 | 实际情况 |
|--------|---------|
| 「问题很简单，用不着走流程」 | 简单问题也有根因，按流程排查这类缺陷很快。 |
| 「情况紧急，没时间走流程」 | 系统化调试比来回猜测和试错更快。 |
| 「先试这个，之后再调查」 | 第一次修复会影响后续做法，从一开始就按流程来。 |
| 「等确认修复有效再写测试」 | 没有测试，修复很容易失效。先写测试才能证明修复有效。 |
| 「一次改好几处能省时间」 | 这样无法判断哪项改动奏效，还容易引入新缺陷。 |
| 「参考实现太长，我自己调整一下就行」 | 理解不完整必然会引入缺陷。把参考实现读完。 |
| 「问题已经看见了，我来修」 | 看到症状之后，还要查明根因。 |
| 「再试一次修复就好」（失败至少两次后） | 失败三次或以上就该审视架构。先检查所用模式，停下修补。 |

## 速查表

| 阶段 | 主要工作 | 完成标准 |
|-------|---------------|------------------|
| **1. 根因** | 阅读错误信息、复现、检查改动、收集证据 | 弄清出了什么问题，以及为什么 |
| **2. 模式** | 查找正常示例并对照 | 找出差异 |
| **3. 假设** | 提出假设并做最小试验 | 证实假设，或提出新假设 |
| **4. 实施** | 编写测试、修复、验证 | 缺陷已解决，测试通过 |

## 排查结果显示「没有根因」时

如果经过系统排查，确认问题确实来自环境、时序或外部因素，则按以下步骤处理。

1. 此时已完成本流程
2. 记录已调查的内容
3. 加入适当的处理方式（重试、超时或错误提示）
4. 添加监控或日志，便于日后调查

**仍要留意** 有 95% 被认为「没有根因」的情况，其实是调查还没做完。

## 配套技术

以下技术是系统化调试的一部分，配套文档都在本目录。

- **`root-cause-tracing.md`** 沿调用栈反向追踪缺陷，找出最初的触发点
- **`defense-in-depth.md`** 查明根因后，在多个层级添加校验
- **`condition-based-waiting.md`** 用条件轮询代替随意设定的超时
